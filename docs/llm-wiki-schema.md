# LLM Wiki Schema Specification v1

**Version:** 1.0 (Draft — context-mem v3.4)
**Status:** Reference spec
**Date:** 2026-04-18
**Audience:** Developers integrating with context-mem, building compatible memory systems, or adopting the LLM Wiki pattern in their own tooling.
**Credit:** Pattern framing from Andrej Karpathy's "LLM Wiki" gist (2026-04-04).

---

## 1. Purpose

This document specifies the on-disk format used by context-mem to store and organize long-term memory as a human-readable, LLM-editable wiki. The format is versioned and documented publicly so that other memory systems, agent frameworks, and tooling can produce or consume a compatible vault without depending on context-mem's internal APIs.

The immediate motivation comes from Andrej Karpathy's "LLM Wiki" gist (2026-04-04), which proposes that language models should maintain a personal wiki of structured knowledge rather than relying solely on raw context windows or opaque vector stores. context-mem implements that idea at the persistence layer: every observation, entity, topic, and synthesized fact lands in a directory of plain Markdown files that any editor, grep, or diff tool can inspect.

This spec covers the directory layout, page types, naming conventions, linking format, ingest and query operations, and the minimum compliance requirements for interoperability. It does not specify the SQLite schema used internally by context-mem — that is an implementation detail. What is specified here is the filesystem projection that the SQLite data is rendered into, because that projection is the interop surface.

Out of scope for v1: real-time synchronization, conflict resolution, CRDT, access control, encryption at rest. Those concerns are deferred to higher layers (e.g. MCP authorization, OS-level file permissions).

---

## 2. The Three Layers (Karpathy Framework)

Karpathy's gist identifies three conceptual layers in an LLM memory system. context-mem maps them as follows.

**Raw sources (immutable).** These are the unedited observations as they were recorded — the verbatim text of a conversation turn, a file diff, a search result, or a code output. In context-mem, raw sources live in `sources/` as one Markdown file per session. Each file is append-stable: new observations are added to the file but existing lines are never modified. The session file is the ground truth for "what was actually seen."

**The wiki (LLM-maintained).** This is the synthesized, cross-referenced layer: entity pages, topic pages, and knowledge pages. These pages are generated and regenerated by the system whenever new information arrives. They summarize, deduplicate, and link. A human editor or an LLM agent can also edit these pages directly to add annotations, correct errors, or promote a claim to a `knowledge/` entry. The wiki is writable; the sources are not.

**The schema (this document).** This layer specifies how the wiki is organized — naming conventions, page structure, linking syntax, operations. The schema is stable across vault instances so that tools can parse any compliant vault without prior knowledge of the domain it covers.

## 3. Directory Layout

A context-mem vault is rooted at a configurable directory, conventionally `.context-mem/vault/` relative to the project root. The full tree:

```
.context-mem/vault/
├── index.md              — Auto-generated table of contents (counts, top entities,
│                           recent topics, recent knowledge). Regenerated on every
│                           pipeline tick. Do not hand-edit in v1; edits are overwritten.
│
├── log.md                — Append-only event log. Each entry is a level-2 heading:
│                           "## [YYYY-MM-DD HH:MM] event | summary". Never truncated.
│
├── schema.md             — Symlink or copy of this document. Auto-linked from index.md
│                           via [[schema.md]].
│
├── sources/              — One file per session. Immutable after the session ends.
│   └── <safeName(session_id)>-<yyyy-mm-dd>.md
│
├── entities/             — One file per named entity (person, project, place, etc.).
│   └── <safeName(entity_name)>.md
│
├── topics/               — One file per detected topic (programming language, domain
│   └── <safeName(topic_name)>.md     concept, recurring theme, etc.).
│
└── knowledge/            — One file per promoted knowledge entry (synthesized facts,
    └── <safeName(knowledge_id)>.md   decisions, procedures, reference material).
```

`sources/`, `entities/`, `topics/`, and `knowledge/` are created by `VaultSync.init()` if they do not exist. A consumer that only reads a vault does not need to create them.

`schema.md` is a convention, not a required file. context-mem places a symlink or copy here so that `index.md`'s `[[schema.md]]` wiki-link resolves locally. A compliant reader must not fail if `schema.md` is absent.

## 4. Page Types

All pages are plain Markdown (CommonMark). v1 uses no YAML frontmatter. Structure is conveyed through heading levels and bullet lists. v1.1 plans to introduce optional YAML frontmatter; a v1-compliant reader must not require it.

### 4.1 Entity Pages

An entity page represents a named thing that appears repeatedly across observations: a person, a project, a file path, an organization, a date-bound event. Pages are auto-generated by `VaultSync.refreshEntity()` and overwritten each time the entity is updated.

**Required fields:**
- H1: entity name (canonical form after alias resolution)
- `Type`: entity_type string (e.g. `person`, `project`, `file`, `location`)
- `Created`: ISO date (YYYY-MM-DD)
- `Updated`: ISO date (YYYY-MM-DD)
- `## Backlinks` section: wiki-links to entities that point to this one via the relationships graph

**Optional fields:**
- `## Metadata` section: JSON block containing arbitrary structured data (confidence, aliases, source observation, etc.)
- Additional H2 sections added by a human editor or LLM agent

**Example rendered page:**

```markdown
# Juba Kitiashvili

- **Type:** person
- **Created:** 2026-03-27
- **Updated:** 2026-04-18

## Backlinks

- [[entities/context-mem]]
- [[entities/gstack]]

## Metadata

```json
{
  "confidence": 0.97,
  "aliases": ["Juba", "JubaK"],
  "source_observation": "01HZ4XQNBVT3K8P9WJFM2CRDG"
}
```
```

If there are no backlinks, the section renders as `_No backlinks yet._`.

### 4.2 Topic Pages

A topic page aggregates observations that share a detected theme or concept. Topics are auto-generated by `VaultSync.refreshTopic()`. The observation list shows the 20 most recent entries ordered by `indexed_at DESC`.

**Required fields:**
- H1: topic name
- `Observations`: total count from the `topics` table
- `Last seen`: ISO date or `never`
- `## Observations` section: bullet list of up to 20 observations (date + summary or first 120 chars of content)

**Example rendered page:**

```markdown
# search architecture

- **Observations:** 47
- **Last seen:** 2026-04-18

## Observations

- [2026-04-18] BM25 strategy 7b (individual synonym search, weight 0.2) shipped in v3.2
- [2026-04-17] LLM judge activates when ai_curation.enabled — Haiku reranker, 50/50 blend
- [2026-04-15] vector search runs in parallel with BM25, not as a cascade fallback
- [2026-04-10] temporal resolver parses "last Saturday" → absolute date range, zero LLM cost
- [2026-03-29] fusion weights: bm25 0.45, trigram 0.15, levenshtein 0.05, vector 0.35
```

### 4.3 Session Pages

A session page is the immutable record of all observations made during one agent or user session. The file name encodes both the session identifier and the date of the first observation.

**File naming:** `<safeName(session_id)>-<yyyy-mm-dd>.md`

The date component is derived from `observations[0].indexed_at` (the earliest observation in the session). If the session has no observations, the current date is used.

**Required fields:**
- H1: `Session <session_id>`
- `Date`: ISO date of first observation
- `Observations`: total count
- `## Observations` section: one bullet per observation, format `[type] summary-or-first-120-chars`

**Example rendered page:**

```markdown
# Session 01HZ4XQ-claude-code-session

- **Date:** 2026-04-18
- **Observations:** 12

## Observations

- [thought] Considered restructuring the BM25 AND-mode weight from 2.0 to 2.2
- [code] Added safeName() edge case test for 200-char cap in vault-templates.ts
- [fact] v3.4.0 target date is 2026-05-01 for LLM Wiki Preview milestone
- [conversation] Discussed Karpathy wiki gist framing with user
- [file_change] Modified src/core/vault-templates.ts — renderLogEntry format confirmed
```

### 4.4 Knowledge Pages

A knowledge page holds a synthesized, promoted fact or reference. Knowledge entries are created explicitly via the `save_knowledge` or `promote_knowledge` MCP tools, not automatically from every observation.

**Required fields:**
- H1: knowledge title
- `Category`: string (e.g. `architecture`, `decision`, `procedure`, `reference`)
- `Created`: ISO date
- `Tags`: comma-separated list or `none`
- `Access count`: integer (incremented on each retrieval)
- `## Content` section: the knowledge body (free Markdown)

**Example rendered page:**

```markdown
# BM25 Strategy Weights (v3.2)

- **Category:** architecture
- **Created:** 2026-04-15
- **Tags:** search, bm25, weights, retrieval
- **Access count:** 8

## Content

Eight BM25 strategies run in parallel for every query, each with an assigned weight:

| Strategy | Weight | Description |
|----------|--------|-------------|
| AND-mode | 2.0 | High precision; all tokens must match |
| Phrase | 1.9 | Consecutive keyword pairs |
| Entity-focused | 1.8 | Proper nouns and dates only |
| Sanitized FTS5 | 1.5 | Default SQLite tokenization |
| Relaxed AND | 1.2 | Entity + top keywords |
| OR + synonyms | 1.0 | Broad recall with synonym expansion |
| Individual keywords | 0.5 | Long-tail catch |
| Individual synonyms | 0.2 | Semantic gap bridge (e.g. "siblings" → "brother") |
| Temporal resolution | 1.6 | Relative dates → absolute keyword ranges |

Weights are applied as score multipliers during result fusion.
```

### 4.5 Index Page

`index.md` is the vault entry point. It is fully auto-generated and overwritten on every call to `VaultSync.refreshIndex()`, which the pipeline triggers after every observation cycle.

**Structure:**
1. H1: `Context-Mem Vault`
2. Blockquote: `Auto-generated. Last updated: YYYY-MM-DD HH:MM`
3. `## Counts` — Markdown table with rows: Observations, Entities, Topics, Knowledge, Sessions
4. `## Top Entities` — up to 10 entities ordered by `updated_at DESC`, each as a wiki-link with last-updated date
5. `## Recent Topics` — up to 10 topics ordered by `last_seen DESC`, each as a wiki-link with observation count
6. `## Recent Knowledge` — up to 10 knowledge entries ordered by `created_at DESC`, each as a wiki-link with title
7. Footer: `_Schema reference: [[schema.md]]_`

**Auto-regeneration rules:**
- Regenerated after every `VaultSync.refreshIndex()` call.
- The pipeline calls `logEvent('ingest', ...)` after each observation; `refreshIndex()` is called separately on entity/topic/knowledge update.
- In v1, the entire file is overwritten. User edits to `index.md` do not survive a regeneration. v1.1 plans to introduce preserved-user-edits markers for custom sections.

**Example rendered page (abbreviated):**

```markdown
# Context-Mem Vault

> Auto-generated. Last updated: 2026-04-18 14:33

## Counts

| Table | Rows |
|-------|------|
| Observations | 1284 |
| Entities | 93 |
| Topics | 41 |
| Knowledge | 17 |
| Sessions | 28 |

## Top Entities

- [[entities/Juba-Kitiashvili]] — updated 2026-04-18
- [[entities/context-mem]] — updated 2026-04-18
- [[entities/BM25]] — updated 2026-04-17

## Recent Topics

- [[topics/search-architecture]] — 47 observations
- [[topics/vault]] — 19 observations

## Recent Knowledge

- [[knowledge/01HZ4XQNBVT3K8P9WJ]]  BM25 Strategy Weights (v3.2)

---

_Schema reference: [[schema.md]]_
```

### 4.6 Log Page

`log.md` is the append-only event journal for the vault. It is never truncated or rewritten. Each entry is appended by `VaultSync.logEvent(event, summary)`.

**Format:** Each entry is a level-2 heading followed by no body:

```
## [YYYY-MM-DD HH:MM] event | summary
```

`event` is a short machine-readable tag (e.g. `ingest`, `entity_update`, `topic_update`, `knowledge_promote`). `summary` is a human-readable string truncated to ~80 characters. The timestamp is UTC, formatted as `YYYY-MM-DD HH:MM` (no seconds).

**Grep recipe for recent ingest events:**

```bash
grep "^## \[" .context-mem/vault/log.md | tail -20
grep "^## \[" .context-mem/vault/log.md | grep "ingest"
```

**Example rendered entries:**

```markdown
# Event Log

## [2026-04-18 14:31] ingest | fact: v3.4.0 target date confirmed as 2026-05-01
## [2026-04-18 14:32] ingest | code: modified vault-templates.ts renderLogEntry
## [2026-04-18 14:33] ingest | thought: considering YAML frontmatter for v1.1
## [2026-04-18 14:33] entity_update | Juba Kitiashvili
## [2026-04-18 14:33] topic_update | vault
```

## 5. Linking Conventions

All cross-references within the vault use wiki-link syntax: `[[target]]`. This syntax is recognized by Obsidian, Foam, Dendron, and most Markdown-based knowledge-base tools. context-mem's renderer produces links but does not resolve them at render time — resolution is left to the reader (tool or human).

### Link targets

| Prefix | Example | Resolves to |
|--------|---------|-------------|
| `entities/` | `[[entities/Juba-Kitiashvili]]` | `entities/Juba-Kitiashvili.md` |
| `topics/` | `[[topics/search-architecture]]` | `topics/search-architecture.md` |
| `knowledge/` | `[[knowledge/01HZ4XQ...]]` | `knowledge/01HZ4XQ....md` |
| (bare) | `[[schema.md]]` | `schema.md` in vault root |

All link targets are relative to the vault root, not to the containing file. A reader must resolve `[[entities/foo]]` as `<vault_root>/entities/foo.md` regardless of which subdirectory the linking file lives in.

### safeName algorithm

File names are derived from the entity name, topic name, or knowledge ID by applying `safeName()`:

```typescript
function safeName(name: string): string {
  const cleaned = name
    .replace(/[/\\:]/g, '-')          // replace / \ : with -
    .replace(/[\x00-\x1f\x7f]/g, '') // strip ASCII control characters
    .replace(/\.\./g, '--')            // collapse .. to -- (path traversal guard)
    .trim();
  return cleaned.length > 0 ? cleaned.slice(0, 200) : '_unnamed';
}
```

Rules in plain English:
1. Replace `/`, `\`, and `:` with `-`.
2. Strip all ASCII control characters (U+0000–U+001F, U+007F).
3. Replace `..` with `--` to prevent path traversal.
4. Trim leading and trailing whitespace.
5. Truncate to 200 characters.
6. If the result is empty, use `_unnamed`.

The algorithm is intentionally minimal. It does not lowercase, does not transliterate Unicode, and does not de-duplicate collisions. If two distinct entity names produce the same `safeName`, the last writer wins. v1.1 may introduce a collision-avoidance suffix.

### Backlinks

Backlinks are computed from the `relationships` table (graph edges `from_entity → to_entity`) and rendered into the `## Backlinks` section of entity pages. They are refreshed each time `VaultSync.refreshEntity()` is called for the target entity. There is no separate backlink index file in v1.

## 6. Operations

### 6.1 Ingest

The ingest operation records a new observation and updates all relevant vault files. The following steps mirror `Pipeline.observe()` plus the vault hooks:

1. **Budget check.** If the session's byte budget is exhausted, the operation is rejected with an error. The vault is not written.

2. **Privacy processing.** Content is scanned for `<private>` tags (stripped entirely) and regex-matched patterns (replaced with `[REDACTED]`). The resulting `privacy_level` is one of `public`, `redacted`, or `private`. Private observations are stored in SQLite but are not rendered into vault pages.

3. **SHA-256 deduplication.** The cleaned content is hashed. If the hash matches an existing observation, the existing record is returned immediately and no vault write occurs.

4. **Entity extraction (deterministic, zero-LLM).** Named entities (people, projects, dates, files) are extracted from the content using pattern matching and a curated gazetteer. Aliases are resolved to canonical names.

5. **Importance classification (deterministic, zero-LLM).** A score and flag set are assigned based on content type, entity presence, and keyword signals. A noise filter (`computeSignalScore`) down-weights observations scoring below 0.3.

6. **Topic detection (deterministic, zero-LLM).** The content is matched against a topic taxonomy. Multiple topics may be assigned with individual confidence scores.

7. **Summarization.** Summarizers are tried in order: (a) LLM summarizer if `llmService` is configured; (b) 14 deterministic pattern-based summarizers; (c) truncation cascade for content exceeding `MAX_PASSTHROUGH`. Pinned observations bypass summarization.

8. **INSERT into observations.** The observation row is written to SQLite with all computed fields: `id` (ULID), `type`, `content`, `summary`, `content_hash`, `privacy_level`, `session_id`, `importance_score`, `pinned`, `compression_tier`.

9. **Vault event log.** `VaultSync.logEvent('ingest', '<type>: <first-80-chars>')` appends one line to `log.md`. This call is fail-open: a log write failure is recorded to `ErrorLogger` but does not abort the observation.

10. **Entity graph update.** Each extracted entity is upserted into the `entities` table via `KnowledgeGraph`. `VaultSync.refreshEntity(name)` regenerates the entity's `.md` file. Fail-open.

11. **Topic association storage.** `storeTopics()` writes `observation_topics` junction rows. `VaultSync.refreshTopic(name)` regenerates the topic's `.md` file. Fail-open.

12. **Embedding (async, non-blocking).** For content under 2000 characters, embedding is computed synchronously using `nomic-embed-text-v1.5` (768-dim) and stored as a binary buffer in the `observations.embeddings` column. For longer content, `setImmediate()` defers the embedding so that `observe()` returns without waiting. Embedding failure is non-critical.

13. **Return observation.** The fully populated `Observation` object is returned to the caller.

Session pages (`sources/<id>-<date>.md`) are regenerated by calling `VaultSync.refreshSession(sessionId)`. This is not called on every single observation to avoid O(n) rewrites; callers may batch this or call it at session close.

### 6.2 Query

The query operation retrieves observations relevant to a natural-language or structured query and optionally surfaces corresponding vault page references.

1. **Intent classification.** The query is analyzed to determine primary intent: keyword lookup, entity lookup, temporal lookup, or semantic lookup. This is deterministic in v1 (pattern matching); the LLM judge path is optional.

2. **Hybrid retrieval (parallel).** Four retrieval strategies run concurrently and their results are fused:
   - **BM25** (weight 0.45 in fusion): 8 sub-strategies run as a waterfall within BM25 — AND-mode, phrase, entity-focused, sanitized FTS5, relaxed AND, OR with synonym expansion, individual keywords, temporal resolution. Each sub-strategy has its own score multiplier (2.0 down to 0.2).
   - **Trigram** (weight 0.15): character-level n-gram similarity; useful for partial matches and misspellings.
   - **Levenshtein** (weight 0.05): fuzzy edit-distance fallback for short tokens.
   - **Vector** (weight 0.35): cosine similarity over 768-dim embeddings; activates only if embeddings are present.

3. **Score fusion.** IDF-weighted content reranker blends keyword density and bigram signals. BM25 and trigram raw scores are normalized to 0–1 before weighting. Negative weights are clamped to 0.

4. **Optional LLM judge reranking.** When `ai_curation.enabled` is true, the top-N candidates are scored 0–10 by Claude Haiku and blended 50/50 with the retrieval score. This step is skipped in the default (LLM-free) configuration.

5. **Result assembly.** The top results are returned as `Observation` objects. For each result, the caller may resolve the session page (`sources/<id>-<date>.md`) and any entity or topic pages linked from that observation for richer context.

### 6.3 Lint

A vault lint pass checks for structural problems that accumulate over time:

- **Orphan entities**: entity pages in `entities/` with no backlinks and no recent observations. Indicator of stale or incorrectly extracted entities.
- **Stale topics**: topic pages where `last_seen` is more than N days in the past relative to the vault's most recent observation.
- **Missing cross-refs**: entity names that appear in observation summaries but have no corresponding `entities/` page (entity extraction may have been skipped or failed).
- **Temporal contradictions**: knowledge pages asserting conflicting dates or version numbers for the same subject.
- **Broken wiki-links**: `[[entities/foo]]` references where `foo.md` does not exist.

As of context-mem v3.4 (2026-04-18), lint results are surfaced via the `diagnostics` MCP tool and the dashboard's Diagnostics page. A dedicated `wiki_lint` MCP tool is planned for v4.0 ("Cognition").

Manual lint using standard shell tools:

```bash
# Find entity links in all vault pages that have no corresponding file
grep -roh '\[\[entities/[^]]*\]\]' .context-mem/vault/ | \
  sed 's/\[\[entities\///;s/\]\]//' | sort -u | \
  while read f; do [ -f ".context-mem/vault/entities/$f.md" ] || echo "MISSING: $f"; done

# Topics not seen in the last 30 days (requires jq or SQLite query)
grep "Last seen:" .context-mem/vault/topics/*.md | \
  awk -F': ' '{print $2, $1}' | sort
```

## 7. Agent Workflows

### For Claude Code / Cursor / Windsurf / Cline / Aider / Continue / VS Code / JetBrains AI

Add the following to `CLAUDE.md` or `AGENTS.md` in the project root to give any agent access to the vault. Adjust the vault path if `vaultDir` is configured differently.

```markdown
## Memory (context-mem vault)

The project's long-term memory lives in `.context-mem/vault/`.

**Before answering any question about prior decisions, history, or context:**
1. Read `.context-mem/vault/index.md` to orient yourself (counts, top entities, recent topics).
2. Use the `search` or `recall` MCP tool to find relevant observations.
3. If an entity or topic is mentioned, read its page directly:
   - `.context-mem/vault/entities/<safeName>.md`
   - `.context-mem/vault/topics/<safeName>.md`
4. Prefer citing page references (`[[entities/foo]]`) over quoting raw observation text.

**After making a significant decision or learning a new fact:**
- Call `mcp__context-mem__observe` to record it.
- Call `mcp__context-mem__save_knowledge` or `mcp__context-mem__promote_knowledge`
  for facts that should survive across sessions.

**Log inspection:**
- Recent events: `grep "^## \[" .context-mem/vault/log.md | tail -20`
- Ingest history: `grep "ingest" .context-mem/vault/log.md | tail -50`

Do not edit `index.md` or `log.md` by hand — they are auto-generated/append-only.
Entity and topic pages may be annotated with additional H2 sections; those annotations
will survive regeneration only in v1.1+.
```

### For CrewAI / LangChain / AutoGen Frameworks

These frameworks expose a pluggable memory driver interface. Point the driver at the context-mem MCP server; agents inherit all 45+ MCP tools including `observe`, `recall`, `search`, `save_knowledge`, and `graph_query`.

**Pattern for LangChain:**

```python
from langchain.memory import ConversationBufferMemory
from langchain_mcp import MCPToolkit  # hypothetical wrapper

# Connect to context-mem MCP server (stdio or HTTP transport)
toolkit = MCPToolkit(server_command=["npx", "context-mem", "--mcp"])
tools = toolkit.get_tools()

# Wrap search and observe as the memory backend
memory = MCPMemory(
    load_tool=toolkit.get_tool("recall"),
    save_tool=toolkit.get_tool("observe"),
)
```

**Pattern for CrewAI:**

```python
from crewai import Agent, Task
from crewai_tools import MCPServerAdapter

context_mem = MCPServerAdapter(
    server_params={"command": "npx", "args": ["context-mem", "--mcp"]},
    tool_names=["observe", "recall", "search", "save_knowledge", "graph_query"],
)

researcher = Agent(
    role="Research Analyst",
    tools=[context_mem],
    memory=True,  # CrewAI's session memory; use context-mem for long-term
)
```

In both patterns, agents read and write through the MCP tools, which drive the full pipeline (privacy, dedup, entity extraction, vault sync) transparently. Direct filesystem reads of vault pages are also valid for read-only consumers that do not need to write new observations.

## 8. Interop Contract

Any tool that claims to produce or consume a compliant v1 vault MUST satisfy the following:

**Producer requirements (writing a vault):**
- MUST create the four subdirectories: `sources/`, `entities/`, `topics/`, `knowledge/`.
- MUST create `index.md` with at least a `## Counts` table.
- MUST create `log.md` with at least the `# Event Log` header.
- MUST name session files as `<safeName(session_id)>-<yyyy-mm-dd>.md` in `sources/`.
- MUST name entity files as `<safeName(entity_name)>.md` in `entities/`.
- MUST use the `safeName` algorithm defined in §5 for all file names.
- MUST use `[[entities/<safeName>]]`, `[[topics/<safeName>]]`, `[[knowledge/<safeName>]]` syntax for internal links.
- MUST NOT include YAML frontmatter in v1 pages (reserved for v1.1).

**Consumer requirements (reading a vault):**
- MUST resolve `[[entities/foo]]` as `entities/foo.md` relative to vault root.
- MUST NOT fail if optional files (`schema.md`, `knowledge/`) are absent.
- MUST treat `log.md` as append-only — no truncation or rewriting.
- SHOULD parse the `## Counts` table in `index.md` for summary statistics.
- SHOULD treat any `.md` file in `entities/` as a valid entity page even if it lacks the full required structure (partial pages from other producers).

**Minimum compliance checklist:**

- [ ] Four subdirectories created on init
- [ ] `safeName` algorithm matches §5 specification exactly
- [ ] Session file naming convention (`<id>-<date>.md`) followed
- [ ] Wiki-link syntax (`[[dir/name]]`) used for all internal references
- [ ] `log.md` is append-only
- [ ] `index.md` contains a `## Counts` table
- [ ] No YAML frontmatter in any page

**Non-goals.** This spec is not a replacement for MCP (which handles transport, authentication, and tool invocation) or CRDT (which handles distributed concurrent edits). It is a filesystem-level convention. Real-time collaboration between two agents writing to the same vault concurrently is out of scope for v1; producers should treat the vault as single-writer.

## 9. Evolution

This is v1. The spec is open for community RFC.

**RFC process:** Open a discussion at `https://github.com/JubaKitiashvili/context-mem/discussions/categories/schema-rfc`. Tag the discussion with `schema-rfc` and reference the section number being amended.

**Planned v1.1 changes:**
- **YAML frontmatter.** Optional YAML block at the top of entity, topic, and knowledge pages. Allows structured metadata (type, tags, created, updated) to be parsed without H1/bullet parsing. v1.1 producers MUST treat frontmatter as optional; v1 consumers that encounter frontmatter SHOULD skip the block and proceed to H1.
- **Typed backlinks.** Backlink entries will carry a relationship type: `derived-from`, `mentions`, or `supersedes`. Current v1 backlinks are untyped.
- **Preserved-user-edits markers.** Auto-generated pages will use HTML comment delimiters (`<!-- auto-generated: start -->` / `<!-- auto-generated: end -->`) to mark sections that will be overwritten. Content outside these delimiters will be preserved across regenerations.
- **SafeName collision avoidance.** A short suffix (first 6 chars of SHA-256 of the original name) will be appended when two distinct names produce the same safeName.

**Version negotiation.** Vault directories SHOULD contain a `_version` file with the schema version string (e.g. `1.0`). Consumers that encounter an unknown version SHOULD degrade gracefully rather than fail.
